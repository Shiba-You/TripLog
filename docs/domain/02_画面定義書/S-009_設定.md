## 状態

通常 / 通知許可待ち / データ削除確認モーダル

## 処理

| No | トリガー | 処理内容 | 呼び出しAPI | クエリ（相当のSQL） |
|---|---|---|---|---|
| 1 | 画面表示 | OS通知許可状態を確認し、通知ON/OFFスイッチの初期状態を反映 | - | - |
| 2 | 通知ON/OFFスイッチをONにする | OS通知許可を要求し、許可されたらAPNsトークンを取得して端末を登録 | `POST /api/devices` | `INSERT INTO devices (id, user_id, platform, apns_token) VALUES (gen_random_uuid(), $1, 'ios', $2) RETURNING id, created_at;` |
| 3 | 通知ON/OFFスイッチをOFFにする | 登録済み端末を解除 | `DELETE /api/devices/{deviceId}` | `DELETE FROM devices WHERE id = $1 AND user_id = $2;` |
| 4 | 位置取得間隔／断絶通知しきい値の変更 | 端末ローカルへ保存（現行APIに保存先未定義） | - | - |
| 5 | データエクスポートボタンのタップ | 旅行・トラック・トラックポイントをGPX/JSON形式で出力（F-021、将来対応） | 未実装（専用APIなし） | - |
| 6 | データ削除ボタン→確認ダイアログで確定 | ユーザーの全データを削除 | 個別削除APIの組み合わせ、または専用の一括削除APIが必要（後述補足） | `DELETE FROM trips WHERE user_id = $1;`（外部キー制約に応じて`tracks`/`track_points`/`photos`/`expenses`/`ai_chat_sessions`等も連動削除される設計を想定）<br>`DELETE FROM visited_regions WHERE user_id = $1;`<br>`DELETE FROM devices WHERE user_id = $1;` |
| 7 | タブバーのタップ | S-001／S-003／S-006へ遷移 | - | - |

## 補足

- 断絶通知しきい値（既定5分）は `docs/01_基本設計/06_API設計.md` の定期ジョブが参照する値だが、現行データモデルにはユーザー単位の設定保存先（例: `users`テーブルへのカラム追加）が無い。端末ローカル保存のみだと「サーバ側の定期ジョブがどのしきい値で判定するか」を解決できないため、実装時に永続化先（`users`テーブル拡張等）の追加を検討する必要がある。
- データ削除は現行API設計に「ユーザー全データ削除」専用エンドポイントが無いため、実装時に追加するか、クライアント側で `DELETE /api/trips/{tripId}` を旅行ごとに繰り返し呼ぶ方式にするかを決定する必要がある（後者はトランザクション保証が弱い）。
