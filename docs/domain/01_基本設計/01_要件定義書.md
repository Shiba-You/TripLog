# 要件定義書

## 1. 背景・目的

旅行の体験は、その場では強く記憶に残るが、時間が経つと「どこをどう巡ったか」「何を見て何にいくら使ったか」が曖昧になっていく。地図上に自分の足跡が残り、訪れた土地が少しずつ埋まっていく可視化があれば、旅の記録は振り返りの資産になり、次の旅行のモチベーションにもなる。

Trip Log は、この「旅の軌跡を自動で記録し、地図上にコレクションとして可視化する」ことを中心価値とする個人向けサービスである。OSSの Adventure Log を参考に、位置トラッキング・写真・家計簿・AI経路提案を一つにまとめ、まずは作者自身が使い込み、将来的にOSS化とApp Store公開につなげることを目的とする。

## 2. スコープ

### 対象とすること（やること）

- モバイルアプリでの位置情報トラッキング（定期ポーリング）と経路の地図マッピング
- 訪問済みエリアの「塗りつぶし」可視化（トロフィー的コレクション）
- GPXファイルのインポート
- トラッキング断絶（通信圏外・充電切れ等）の検知と通知
- 旅行中に撮影した写真の自動同期と撮影地点へのマッピング
- 旅行ごとのラベリングと、地図上での色分け可視化
- 旅費の家計簿（記録・一覧・集計）
- AIによるおすすめ経路チャット
- PCブラウザでのダッシュボード閲覧、およびGPX/画像のアップロード

### 対象外とすること（今回やらないこと）

- 複数ユーザー間の共有・SNS的な公開機能（将来検討）
- Androidアプリ（React Native採用により将来展開はしやすくしておくが、初期スコープ外）
- 他者とのリアルタイム位置共有
- 経路の自動ナビゲーション（ターンバイターン案内）
- 決済・課金機能

## 3. 想定ユーザー

| ユーザー種別 | 説明 | 主な利用シーン |
|---|---|---|
| 作者本人（初期の唯一のユーザー） | サービスの作者かつ利用者。技術的な前提知識がある | 旅行中にトラッキングを開始し、帰宅後にWebダッシュボードで振り返る |
| 将来の個人ユーザー（OSS/AppStore） | 旅の記録を残したい個人。非技術者も含む | 自前ホスト、または公開版アプリで自分の旅を記録・可視化する |

## 4. 機能要件

システムが「できること」を以下に示す（詳細と優先度は `02_機能一覧.md` と整合）。

- 旅行（トリップ）を作成し、名称・期間・ラベル色を設定できる
- モバイルでトラッキングモードを開始/一時停止/終了でき、位置情報を定期的に取得して経路として記録できる
- 取得した経路を地図上に、旅行ごとの色で可視化できる
- 訪問済みエリア（国/都道府県/市区町村などの行政区画単位）を判定し、地図上で塗りつぶして表示できる
- 訪問済みエリアの累計（訪問数・カバー率など）を統計として表示できる
- トラッキング中に一定時間（既定5分）位置取得が途絶えた場合、通知を送れる
- GPXファイルをアップロードして経路として取り込める
- 旅行中に撮影した写真を自動的に取得・同期し、撮影地点（EXIFのGPS、無ければ撮影時刻と経路の突合）にマッピングできる
- 写真を地図上のピンおよびギャラリーとして閲覧できる
- トラックおよび写真に対してコメント（感想・日記）を複数残せ、時系列で振り返れる。旅行中に日記感覚で書き足せる
- メインのマップ画面に、撮影した写真を撮影地点のピンとして表示できる（経路・訪問エリアと重ねて閲覧できる）
- 旅費を費目・金額・日時・メモ付きで記録し、旅行ごとに一覧・集計できる
- 次の目的地に困ったとき、AIにおすすめ経路や立ち寄り先を相談できる
- PCブラウザでダッシュボード（地図・統計・旅行一覧・写真・家計簿）を閲覧でき、GPX/画像をアップロードできる

## 5. 非機能要件

### 性能
- 位置情報の点はモバイル側でバッファリングし、まとめて（バッチで）APIへ送信する。圏外時はローカルに蓄積し、復帰時に再送する。
- 地図はベクタータイル（PMTiles）で描画し、経路・訪問エリアはGeoJSON/ベクターレイヤーのオーバーレイとして表示する。1旅行あたり数万点規模のトラックポイントでも、地図表示時はズームに応じて間引き（簡略化）して描画する。
- API応答時間は、一般的な取得系で 300ms 以内（自宅サーバ・国内アクセス想定）を目標とする。

### 可用性
- 初期は自宅サーバのためベストエフォート。常時稼働は前提としない。
- データ消失を防ぐため、DBは定期的に `pg_dump` し、暗号化のうえR2へ退避する（日次cronを想定）。

### セキュリティ
- 認証は当面なし（単一ユーザー）。ただし自宅サーバをインターネットに公開する場合に備え、APIは共有シークレット（APIキー）による簡易保護を推奨する（任意・既定で有効化を推奨）。
- 通信はHTTPS必須（リバースプロキシ Caddy + Let's Encrypt を想定）。
- 写真はR2へ直接アップロードし、署名付きURL（短時間有効）経由でやり取りする。
- **位置情報は機微な個人データ**である点に留意し、バックアップは暗号化し、ログに生の座標を残さない方針とする。

### 拡張性 / 保守性
- 将来のマルチユーザー化を見据え、全データに `user_id` を持たせる（MVPでは単一ユーザーをシード）。公開フェーズでは認証＋行レベルセキュリティ（RLS）を追加する。
- DBスキーマはマイグレーションファイルで管理し、自宅PostgreSQL → Supabase / AWS RDS への移行を容易にする。
- 地図はレンダラ（MapLibre）とタイル（PMTiles）を分離し、タイル供給元を差し替え可能にする。

### 対応環境
- iOS: 16以降（React Native / maplibre-react-native の対応水準に準拠）
- PCブラウザ: 最新の Chrome / Edge / Safari / Firefox（Windows / Mac）
- 表示言語: 日本語（初期）。将来i18n対応の余地を残す。

## 6. 前提・制約

- 予算は極力抑える（スモールスタート）。マネージドサービスの無料枠・低コスト構成を優先する。
- インフラは「自宅サーバをAPIサーバとして開始 → 形になり次第AWSへ移行」する段階的方針。
- DBは「自宅サーバに PostgreSQL + PostGIS を自前運用」で開始し、公開フェーズで Supabase（東京リージョン）または AWS RDS/Aurora への移行を想定。
- 地図は「MapLibre GL ＋ Protomaps PMTiles（R2自前ホスト）」を基本とし、日本国内の鮮度が必要な場面では地理院タイルを併用可能とする。
- 写真など大容量バイナリはDBに格納せず、Cloudflare R2 に外出しする。
- AIチャットは Claude（Anthropic）API を利用する。
- iOSアプリは React Native で実装する（将来のAndroid展開・OSS化のしやすさを考慮）。なお maplibre-react-native は Expo Go では動作せず、Dev Build / EAS Build が必要である点を前提とする。
- （前提として設定）写真同期は iOS の PhotoKit で旅行期間中の撮影写真を取得し、EXIFのGPS、無ければ撮影時刻とトラックの突合で地点を決定する。

## 7. 用語集

| 用語 | 定義 |
|---|---|
| トリップ（Trip / 旅行） | ラベル付けの単位。1回の旅行を表し、名称・期間・色を持つ |
| トラック（Track） | 1回のトラッキングセッション、またはインポートした1本のGPX。1トリップに複数持てる |
| トラックポイント（Track Point） | 位置情報の1点（緯度経度・時刻・高度・精度など） |
| カバレッジ（Coverage） | 訪問済みエリアの集合。行政区画単位で判定する |
| トロフィー | カバレッジを「埋まっていくコレクション」として可視化したUI上の概念 |
| PMTiles | 全タイルを1ファイルに収めた読み取り専用のタイルアーカイブ形式。サーバ不要で自前ホストできる |
| PostGIS | PostgreSQLの地理空間拡張。空間型・空間インデックス・空間関数を提供する |
| GPX | GPSの軌跡を表す標準的なXMLフォーマット |
| APNs | Apple Push Notification service。iOSへのプッシュ通知基盤 |
| EXIF | 写真ファイルに埋め込まれる撮影メタデータ（GPS座標・撮影時刻など） |
| RLS | Row Level Security。行単位のアクセス制御。マルチユーザー化時に利用 |
