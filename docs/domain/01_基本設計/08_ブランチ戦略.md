# ブランチ戦略

## 方針

GitHub Flow をベースにしたシンプルなブランチ運用とする。個人開発かつ将来のOSS化を見据え、Git Flowのようなrelease/hotfixブランチを持つ複雑な運用は現段階では過剰と判断し採用しない。

## ブランチ一覧

| ブランチ | 用途 |
|---|---|
| `main` | 常にリリース可能な状態を維持する。直接pushは行わず、PRのマージのみで更新する |
| `feature/<機能名>` | `main` から作成する作業ブランチ。1つの機能・修正単位で作成し、完了したら `main` へPRを出す |

`<機能名>` は kebab-case とし、対象の画面IDがある場合は含める（例: `feature/s-001-trip-list`、`feature/fix-track-point-index`）。

## フロー

```mermaid
gitGraph
    commit id: "release"
    branch feature/s-001-trip-list
    checkout feature/s-001-trip-list
    commit id: "impl 1"
    commit id: "impl 2"
    checkout main
    merge feature/s-001-trip-list id: "PR承認・マージ"
    branch feature/fix-track-point-index
    checkout feature/fix-track-point-index
    commit id: "fix"
    checkout main
    merge feature/fix-track-point-index id: "PR承認・マージ"
```

## PRルール

- `feature/*` → `main` へのPRのみを行う（`main` からの直接push・force pushは禁止）
- **PRを作成する時点で、対象ワークスペース（`api` / `web` / `mobile`）の全テストが成功していること**が必須条件。テストが通っていない状態のPRは作成しない
- レビュー承認（最低1名）を得てからマージする
- マージ後、不要になった `feature/*` ブランチは削除する

CIによる自動テスト実行とブランチ保護ルール（必須ステータスチェック）の整備は別タスクとする（現時点でCI/CDは未整備。`docs/domain/01_基本設計/07_基盤設計.md` の「今回のスコープ外」参照）。整備するまでは、PR作成者がローカルで全テストを実行し成功を確認したうえでPRを出す運用とする。

## リリース運用

`main` へのマージ = リリース可能な状態。実際のデプロイ（自宅サーバー、将来的にAWS）はCI/CD整備後は自動化を検討するが、現時点では手動で行う。
